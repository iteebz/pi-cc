# Known issues

## Prompt cache miss rate is ~25% (CC/Anthropic baseline)

The ~25% miss rate is not bridge damage — it is the CC baseline. Measured:
plain resume (no rebuild) misses **26%**, rebuild misses **22%**. Rebuilds
are not measurably worse than native resumes.

The bridge's conversion is lossy (thinking blocks dropped from other
providers, tool IDs sanitized, aborted turns dropped), but this does not
cause the misses. Anthropic's prompt cache has its own TTL, eviction, and
routing behavior that dominate.

The lever for better cache hits is fewer rebuilds, not better conversion.
The code already optimizes: same UUID across rebuilds, cursor tracking,
REUSE path whenever possible. See `diag/AUDIT.md` for the full
investigation.

## Files CC edits aren't carried across rebuilds

CC records post-edit contents as `edited_text_file` attachments; those aren't
carried (they hang off tool-result records with no stable position). The edit
itself survives as a tool call + result. `@file` expansions *are* carried
(`src/attachments.ts`).

## Claims about CC behavior

`~/.claude/projects/**` is **not** evidence of what CC does — the bridge writes
the same files, and CC re-serializes imported records under synthetic ids.
Before asserting "CC does X" from disk, split by provenance (CC-live records
have real `requestId`/`promptId`; ours have `msg_syn_*`/`req_syn_*`).

Better: prove it with a live probe. `tests/int-cc-contracts.mjs` pins
undocumented behaviors against the installed SDK. `diag/capture-proxy.mjs`
captures actual request bodies. And before reverse-engineering an SDK option,
grep `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts` — it documents
every settings field.

## CC source audit (2026-08-26)

Full audit in `docs/cc-source-audit.md`, verified against CC 2.0.89 source.

**All five seams verified:**

1. **JSONL fields** — all correct or inert. `uuid`, `parentUuid`, `timestamp`,
   `isSidechain`, `message.id` are load-bearing and the bridge writes them
   correctly. `userType`, `requestId`, `slug`, `entrypoint` are never read by
   normalization. `version` (hardcoded `"2.1.83"`) and `gitBranch` (hardcoded
   `"HEAD"`) are cosmetic fragilities — no normalization impact, but future CC
   versions could gate behavior on them.

2. **Tool pairing** — bridge and CC repairs are compatible and idempotent. No
   double-repair is possible. Bridge writes synthetic `is_error` results with
   `"[no tool result recorded]"` — CC sees these as validly paired and skips them.

3. **Attachment lifecycle** — placement matches CC's `reorderAttachmentsForAPI`
   expectations. Only `type: "file"` is carried; everything dropped is either
   reproduced in pi's history or regenerated by CC every turn.

4. **System prompt forwarding** — clean replacement, no interaction with CC's
   cache_control logic. CC's `buildSystemPromptBlocks` operates normally on the
   forwarded string.

5. **Feature flags** — GrowthBook flags (`tengu_toolref_defer_j8m`,
   `tengu_chair_sermon`) can flip normalization mid-session → cache miss. This is
   the CC baseline, not bridge damage. The bridge's content passes through correctly
   regardless of flag state. `tengu_anti_distill_fake_tool_injection` (claude.ts:307)
   could inject unexpected content, but only fires for suspected distillation.

**No fixes needed.** The bridge's assumptions about CC's JSONL processing are correct.
